## 二、报告有一处对返回契约的误读

> "以上 4 种情况中，`candidate_count` 始终为 0 —— 知识图谱本身从未检索到任何匹配"

`candidates` 是**原子工具链**（fastp → bwa → samtools → …）。业务流程（整卡）
推荐走的是 `recommendations`，它的数据证据在 `recommendation.data` 里，不在
`candidate_count` 上。整卡推荐的 `candidate_count` 为 0 是契约设计，不是检索失败。

以"肝癌 HER2 表达和 PFS"为例，当前后端返回：

```json
"data": {
  "status": "available", "matched_count": 3, "expected_count": 3,
  "study_accessions": ["HRA001272"],
  "assets": [{ "file_path": "/hpcdisk1/cbb_group/data/analysis/HRA001272/RNAseq/HRA001272-Genes-TPM-1.0.tsv",
               "source": "T2", "match_reason": "文件名精确匹配" }, ...]
},
"execution_params": { "clinical_xls": "...", "tpm_matrix": "...", "metainfo_xlsx": "..." }
```

判断"有没有命中知识图谱"应该看 `recommendation.data.status` 与 `matched_count /
expected_count`，以及 `execution_params` 是否被真实路径填满。

## 三、报告中属于调用侧的部分

### 3.1 「9 个工具只有 4 个可用」——那 5 个的工具调用列表是空的

报告自己记录了这 5 条的"工具调用：**无**"，即调用侧的 agent 没有发起
`route_pipeline_request`。同样的问题原句直接打 MCP，5 条全部匹配正确：

| 报告原句 | 报告结果 | 当前 MCP 实测 |
|---|---|---|
| 肝癌 TPM 表达矩阵能做免疫浸润分析吗？ | ❌ 未触发 | `immune_infiltration_iobr`，队列 HRA001272 |
| 食管癌 counts 数据怎么做无监督聚类？ | ❌ 未触发 | `rnaseq_unsupervised_cluster` |
| 肝癌 MAF 文件怎么画突变景观图？ | ❌ 未触发 | `wes_somatic_maf_landscape`，数据 available 1/1 |
| RNA-seq FASTQ 原始数据怎么做完整上游分析？ | ❌ 未触发 | `rnaseq_singletask`，`status=ready`，2 条候选链 |
| 胶质瘤 counts 矩阵怎么做 WGCNA？ | ❌ 未触发 | `wgcna`，队列 HRA000074 |

匹配成功率的问题出在"要不要调这个工具"的决策上，不在匹配本身。

### 3.2 `gene=XXX6` 这个参数不是 MCP 填的

报告 3.3 的参数面板里有 `gene`、`winsor_lower/upper`、`docker_image`。

`her2_pfs_survival` 在 MCP 侧声明的输入只有三个文件槽（`clinical_survival`、
`tpm_matrix`、`sample_metainfo`），`execution_params` 也只返回这三个路径。
`gene`、`winsor_*`、`docker_image` 这些字段在本仓库**全文搜索不到**，是调用侧或
WDL 默认值填入的。"把问题中任意一个词当作基因名填进参数"这个动作发生在 MCP 之外。

MCP 侧相关的改动见第四节第 3 条。

### 3.3 报告引用的几段文案不是 MCP 的

以下字符串在本仓库不存在，来自调用侧 agent：

- "候选组合无法可靠区分，请在右侧选择一个 Pipeline + Study 组合"
- "我先按你的原始需求启动标准分析编排"
- "我不能直接绕过固定流程去枚举 Study 列表"

### 3.4 纯前端

上传按钮 disabled 且无 `input[type=file]`、语音按钮无响应、"修改方案"无反应、

以及"HRA001272 有多少样本"被错误路由到 `query_healthy_traits`。

## 四、已修复：确属 MCP 的问题

### 1. 基准里 5 个文件名后缀写错，导致临床表被判为缺失

`config/question_tool_data_benchmark.json` 引用 `HRA001272-Clinical-1.0.xls`，
而图里从 0811 到 0812 一直是 `.xlsx`。图中 20 个 clinical 文件里 18 个为 `.xlsx`。

后果：走"96 例基准命中"这条路时该文件匹配不上，`data.matched_count` 只有 2/3，
`execution_params` 缺 `clinical_xls`，调用侧拿到一个无法提交的方案，且不报错。
走 LLM 那条路反而能填上（它用的是图里的真实路径），两条路结论不一致。

**改动**：按图核对后修正 5 个文件名共 36 处引用。

```
HRA000074 / HRA001272 / HRA003107 / HRA007167 / HRA007169
  -Clinical-1.0.xls  →  -Clinical-1.0.xlsx
```

修完基准引用的 26 个数据文件在图里全部存在。同一条问题现在返回
`execution_params_missing: []`。

**防复发**：新增集成测试
`RealNeo4jIntegrationTests.test_every_benchmark_asset_name_exists_in_the_graph`，
断言基准引用的每个文件名都能在图里找到。这类错误以后会在回归中直接失败，而不是
悄悄降级成一个不可提交的方案。

### 2. 假基因不再被静默当成合法参数

报告 3.1/3.3 的现象复现了：`XXX6` 照样推 `her2_pfs_survival`。要说清能修到什么
程度——**图谱只到文件级，没有基因、位点、通路维度，本服务也不读取文件内容**，
所以"`XXX6` 是不是真基因、在不在这个 TPM 矩阵里"在 MCP 侧无法判定。把它硬判为
不支持是假装有校验能力，比不校验更糟。

改成把这个盲区显式写进返回契约。`recommendations[]` 新增字段：

```json
"unvalidated_parameters": [
  { "parameter": "gene",
    "value_from_question": "XXX6",
    "validated": false,
    "reason": "图谱只到文件级，没有基因维度，本服务无法确认该符号是真实基因、也无法确认它出现在流程要读取的表达矩阵里。",
    "action": "提交前请由执行端或调用方校验；未校验就执行可能得到空结果或报错。" }
]
```

只要流程描述里带"基因/gene"且没有把 gene 声明成正式槽位，就会带上这个字段，
`HER2` 这类真实基因同样申报（MCP 无法区分真假，这正是要申报的原因）。

**调用侧需要配合**：拿到 `unvalidated_parameters` 时，要么在提交前自行校验，
要么在界面上明示"该参数未经校验"，不要直接当成已确认参数渲染。

同时给规划器加了一条硬边界（提示词第 9 条）：不得输出"可将目标基因替换为
XXX"这类断言。报告 3.2 里那句 `match_note: "该pipeline可用于分析任意基因（如
XXX6）…"` 就是这么来的，现在措辞只陈述流程按指定基因分层，不对符号有效性表态。

### 3. 兜底文案把内部措辞暴露给了终端用户

"苹果的红色程度和 PFS 有关系吗"这类问题在无 LLM 理由时会返回
`unsupported_reason: "LLM 未返回可评估的原子工具候选链。"`——这句是说给开发看的，
用户看到它既不知道发生了什么，也不知道下一步该做什么。

**改动**：改成面向用户、给出下一步的说法。

```
没能把这个需求对应到任何已登记的分析能力；如果确实是生信分析需求，
请说明输入数据类型（如 FASTQ / BAM / 表达矩阵 / MAF）和想要的结果。
```

### 4. 顺带修掉一个一直没被发现的坏测试

`test_local_instance_and_known_pipeline` 拿图里的 51 个 `:tool` 节点去比运行时
目录的 50 个（multiqc 被排除在原子层之外），又把 `rnaseq_singletask` 的步数硬编码
成 7（移除 multiqc 后是 6）。它只在 `RUN_REAL_INTEGRATION=1` 时执行，所以日常
回归一直跳过、没暴露。现在两处都改成从契约读取，并加断言确认步骤里不含 multiqc。

## 五、未修复：已知能力边界

以下不是缺陷，是当前设计边界，列出来是为了对齐预期。

| 现象 | 说明 |
|---|---|
| 元数据类问题一律 `unsupported` | "队列有多少样本""临床表有哪些字段"属于数据检索，目录里没有对应的业务流程或原子工具。当前返回明确理由而不是硬塞进方案匹配。是否要接一个元数据查询能力可另议 |
| 匹配走"96 例基准 + LLM 语义"两条路 | 基准是已审核的问题-数据-工具映射，命中即返回；未命中才交给 LLM。报告称其为"固定答案库"，这一层是刻意的：它保证已审核用例的结论稳定可复现 |
| 不做癌种与队列的强校验 | 推荐会给出 `data.study_accessions` 和真实文件路径，但不拒绝"癌种与队列不符"的组合。需要强约束的话要先定义规则 |
