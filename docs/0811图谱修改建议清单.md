# 0811 图谱修改建议清单

> 面向 0811 知识图谱的维护方。
> 下面 6 条是我们在把 0811 图谱接进流程规划器时发现的问题，每条都注明了证据、
> 具体改哪个文件哪一行、以及不改会造成什么后果。所有结论都可以用文末的脚本复现。
>
> 需要说明的是：数据本身导入得很干净，30 个 CSV 的外键零悬空，节点关系数与你们
> 自带的实例逐项一致。下面这些是词表层面的问题，不影响导入，但会影响"工具能不能
> 找到数据"。

---

## 高优先级

### 1. fastqc（T002）的输入输出标注

**现象**

`entities/tool.csv` 里 T002 的两个语义字段是：

```
semantic_input  = RAW_SINGLE_END_FASTQ
semantic_output = RAW_SINGLE_END_FASTQ
输入格式         = FASTQ
输出格式         = HTML, ZIP        ← 这一列是对的
```

**证据**

- **输出对不上**：物理格式列已经写了 `HTML, ZIP`，说明产出的是质控报告；但
  `semantic_output` 写成了 FASTQ。同类工具 T001 fastp、T004 trim_galore 的
  `semantic_output` 都含 `QC_STATS_REPORT`，只有 fastqc 例外。
- **输入匹配不到数据**：`RAW_SINGLE_END_FASTQ` 在 T1 和 T2 里的文件数都是 **0**。
  实际数据全部是成对的 `RAW_PAIRED_END_R1_FASTQ`（13,027 个）和
  `RAW_PAIRED_END_R2_FASTQ`（13,026 个）。

**建议怎么改**

| 文件 | 位置 | 现在 | 改成 |
|---|---|---|---|
| `entities/tool.csv` | T002 行 `semantic_input` | `RAW_SINGLE_END_FASTQ` | `RAW_PAIRED_END_R1_FASTQ; RAW_PAIRED_END_R2_FASTQ` |
| `entities/tool.csv` | T002 行 `semantic_output` | `RAW_SINGLE_END_FASTQ` | `QC_STATS_REPORT` |
| `relations/tool_has_semantic_input.csv` | 第 4 行 | `T002,RAW_SINGLE_END_FASTQ` | 拆成两行 `T002,RAW_PAIRED_END_R1_FASTQ` 和 `T002,RAW_PAIRED_END_R2_FASTQ` |
| `relations/tool_has_semantic_output.csv` | 第 5 行 | `T002,RAW_SINGLE_END_FASTQ` | `T002,QC_STATS_REPORT` |

如果确实要保留单端支持，输入可以三个都列，但 `RAW_SINGLE_END_FASTQ` 目前没有对应数据。

**不改会怎样**

- fastqc 声明的输入在库里一个文件都匹配不到，**任何"用 fastqc 做质控"的需求都排不出流程**。
- `next_tool` 里 `T001(fastp) -> T002(fastqc)` 标的是 `data` 边，但 fastp 的输出
  （R1/R2）和 fastqc 的输入（单端）没有交集。这是你们 10 条 data 边里**唯一一条
  推导不出数据传递关系**的。
- fastqc 的输出被当成 FASTQ 后，下游工具会误以为可以从 fastqc 拿到测序 reads 继续比对。

### 2. `METADATA_SAMPLEINFO` 与 `METADATA_SAMPLE_INFO` 拼写分裂

**现象**

`reference/formats.csv` 里同时存在这两个语义格式，描述说的是同一件事（样本元数据表）。

**证据**——两个拼写的使用是完全互斥的：

| 拼写 | 工具侧引用 | 数据侧文件数 |
|---|---:|---:|
| `METADATA_SAMPLEINFO`（无下划线） | **13** | **0** |
| `METADATA_SAMPLE_INFO`（有下划线） | **0** | **20** |

交集为零。工具只认前者，数据只标后者。

涉及的 13 个工具：`T044 cox_model`、`T047 de_enrichment`、`T048 deg_enrichment`、
`T049 deg_trend`、`T050 gene_boxplot`、`T054 ipf_trajectory_regulon`、`T055 km_survival`、
`T060 scrna_cell_communication`、`T061 stage_heatmap`、`T062 tcell_intervention`、
`T063 umap`、`T065 wgcna_hub`、`T066 wgcna_module_trait`。

**建议怎么改**

统一到 `METADATA_SAMPLE_INFO`（数据侧已在用，改动面更小）：

| 文件 | 改法 |
|---|---|
| `reference/formats.csv` | 删掉 `METADATA_SAMPLEINFO` 那行；如果它的描述更完整，把描述并进保留的那行 |
| `relations/tool_has_semantic_input.csv` | 13 行的 `METADATA_SAMPLEINFO` 全部改成 `METADATA_SAMPLE_INFO` |
| `entities/tool.csv` | 上述 13 个工具的 `semantic_input` 列同步改 |

**不改会怎样**

这 13 个工具（生存分析、富集、WGCNA、单细胞通讯、UMAP 等）**全都声明需要样本元数据
表，但永远匹配不到库里那 20 个元数据文件**。也就是说这一整批分析流程在数据可用性
判定上都会显示"缺少输入"。

## 中优先级

### 3. BAI 索引文件没有任何工具消费或产出

**现象**

`DNA_ALIGNMENT_INDEX_BAI` 在库里有 **6,177 个文件**，但工具表里既没有工具声明它作为
输入，也没有工具声明产出它。

**证据**——对比另一种索引就能看出这不是有意为之：

| 索引类型 | 工具输入 | 工具输出 | 库里文件数 |
|---|---:|---:|---:|
| `DNA_VARIANT_INDEX_TBI`（VCF 索引） | 1 | 3 | 5,788 |
| `DNA_ALIGNMENT_INDEX_BAI`（BAM 索引） | **0** | **0** | **6,177** |

VCF 索引是有工具消费和产出的，说明索引类文件并没有被系统性排除在建模之外，
BAI 是单独遗漏了。而 BAM 索引在变异检测里是必需输入。

当前 T007/T008 的声明：

```
T007 samtools  输入: DNA_GENOMIC_ALIGNMENT_BAM
               输出: DNA_GENOMIC_ALIGNMENT_BAM, QC_STATS_REPORT
T008 gatk      输入: DNA_GENOMIC_ALIGNMENT_BAM, TARGET_INTERVAL_LIST, REFERENCE_GENOME_FASTA
               输出: DNA_GENOMIC_ALIGNMENT_BAM, QC_STATS_REPORT, DNA_VARIANT_VCF_GENERAL, DNA_VARIANT_INDEX_TBI
```

**建议怎么改**

| 文件 | 增加的行 | 说明 |
|---|---|---|
| `relations/tool_has_semantic_output.csv` | `T007,DNA_ALIGNMENT_INDEX_BAI` | samtools 排序建索引后产出 BAI |
| `relations/tool_has_semantic_input.csv` | `T008,DNA_ALIGNMENT_INDEX_BAI` | GATK 变异检测需要 BAM 索引 |
| `entities/tool.csv` | T007 `semantic_output`、T008 `semantic_input` 同步 | |

如果 GATK 也会产出重校正后的 BAI，`T008` 的输出建议一并补上。

**不改会怎样**

库里 6,177 个 BAI 文件是**孤立的**——没有任何流程会用到它们，也说不清它们是谁产生的。
从数据溯源角度看，这批文件在图里断链了。

### 4. 语义格式缺少父子关系

**这一条不是标注错误，你们的标注是对的**，是模型少一层表达能力。

**现象**

所有工具的 BAM 输入都写 `DNA_GENOMIC_ALIGNMENT_BAM`，而库里 6,177 个 BAM 全部标成
`DNA_ALIGNMENT_BQSR_BAM`。两者在词表里是平级的独立概念，工具因此匹配不到数据。

**证据**——我们核对过，你们的标注更准确：

```
文件名样式:  hrr#.bqsr.bam     6177/6177
含 bqsr 或 recal 的比例:        6177/6177
```

这些文件确实都经过 BQSR 处理，标成更具体的 `DNA_ALIGNMENT_BQSR_BAM` 比标成通用 BAM
更精确。两条描述本身也是包含关系：「经过 BQSR 处理后的 DNA 比对 BAM」显然是
「标准 BAM」的子类。问题只是词表里表达不出这层关系。

**影响面**——库里有 **16,457 个文件（占全部 `in_format` 关系的 26%）** 的语义格式
没有任何工具声明为输入，其中相当一部分是这种"数据标得更细、工具写得更粗"造成的：

| 语义格式 | 文件数 |
|---|---:|
| `DNA_ALIGNMENT_BQSR_BAM` | 6,177 |
| `DNA_ALIGNMENT_INDEX_BAI` | 6,177 |
| `OTHER_UNCLASSIFIED_DATA` | 2,246 |
| `DNA_VARIANT_STATS_REPORT` | 603 |
| `RNA_SPLICEJUNCTION_TAB` | 430 |
| `SCRNA_MATRIX_H5` | 403 |
| `DNA_SOMATIC_SV_VCF` | 286 |
| 其余 6 种 | 135 |

**建议怎么改**

新增一张 `reference/format_subclass.csv`，两列 `child,parent`：

```csv
child,parent
DNA_ALIGNMENT_BQSR_BAM,DNA_GENOMIC_ALIGNMENT_BAM
DNA_SOMATIC_SV_VCF,DNA_VARIANT_VCF_GENERAL
SCRNA_MATRIX_H5_ZIP,SCRNA_MATRIX_H5
```

导入时建成 `(:format)-[:subclass_of]->(:format)`，匹配工具输入时沿这条边向上找父类。

上面三行是我们比较有把握的，供参考。下面这几个也在"数据有、工具不认"的名单里，
但是否该挂父类需要你们判断，我们不敢替你们定：
`DNA_VARIANT_STATS_REPORT`、`RNA_SPLICEJUNCTION_TAB`、`SCRNA_MATRIX_H5`、
`SOMATIC_CNV_TSV`、`BIO_DATA_CONTAINER_OBJECT`、`OTHER_UNCLASSIFIED_DATA`。

**不改会怎样**

按语义格式做"工具能吃哪些数据"的匹配时，这 6,177 个 BQSR BAM 对所有工具都是不可见的。
任何"从已有 BAM 出发做变异检测"的需求都会判定为无数据可用。

## 低优先级

### 5. 删掉零引用的 `MUTATION_ANNOTATION_FORMA_MAF`

**现象**

`reference/formats.csv` 第 13 行是 `MUTATION_ANNOTATION_FORMA_MAF`（少一个 T），
第 26 行是正确的 `MUTATION_ANNOTATION_FORMAT_MAF`。

**证据**

| 拼写 | 工具输入 | 工具输出 | T1 | T2 |
|---|---:|---:|---:|---:|
| `MUTATION_ANNOTATION_FORMA_MAF` | 0 | 0 | 0 | 0 |
| `MUTATION_ANNOTATION_FORMAT_MAF` | 4 | 2 | 0 | 2,355 |

前者**零引用**。而且正确那条的描述里写着「旧 T2 对 *.maf 的实际标注；tool 表 FORMA
拼写已归一」，说明拼写已经修过了，只是旧节点没删掉。

**建议怎么改**：删掉 `reference/formats.csv` 第 13 行。

**不改会怎样**：不影响功能，只是图里多一个永远匹配不到任何东西的孤立节点，
`format` 节点数会从 30 变成 29。做数据核对时容易被误认为是漏标。

### 6. `fastp -> bwa` 的 kind 建议确认为 data

**现象**

`relations/tool_relationship.csv` 里：

```
第 3 行:  T001(fastp) -> T005(star)  kind=data
第 4 行:  T001(fastp) -> T006(bwa)   kind=order
```

**证据**——两条边两端的语义格式交集情况相同：

| | fastp 输出 | 下游输入 | 交集 |
|---|---|---|---|
| → star | R1, R2, QC_STATS_REPORT | R1, R2, REFERENCE_GENOME_FASTA | **R1 + R2** |
| → bwa | R1, R2, QC_STATS_REPORT | R1, R2, REFERENCE_GENOME_FASTA | **R1 + R2** |

两条边的数据传递关系完全一样，但一条标 `data` 一条标 `order`。

**建议怎么改**：`tool_relationship.csv` 第 4 行的 `kind` 由 `order` 改为 `data`。
（若确有业务理由认为 fastp 到 bwa 只是执行顺序而没有数据传递，请告知，我们按你们的来。）

**不改会怎样**

`order` 边表示"只有先后顺序、没有数据流"，规划器不会把 fastp 清洗后的 FASTQ 接到
bwa 上，WES 比对链会在这一步断开。我们目前在自己这侧按 `data` 处理了，如果你们那边
统一改掉，两边就一致了。

## 附：如何复现上述统计

```bash
# 每个语义格式在"工具侧"和"数据侧"各出现多少次
python3 - <<'PY'
import csv, collections
R = lambda p: list(csv.DictReader(open(p, encoding='utf-8-sig')))
ti = collections.Counter(r['format'] for r in R('relations/tool_has_semantic_input.csv'))
to = collections.Counter(r['format'] for r in R('relations/tool_has_semantic_output.csv'))
d  = collections.Counter(r['semantic_format'] for r in R('relations/T1_in_format.csv'))
d += collections.Counter(r['semantic_format'] for r in R('relations/T2_in_format.csv'))
for f in sorted(set(ti) | set(to) | set(d)):
    print(f'{f:34} 工具输入={ti[f]:3} 工具输出={to[f]:3} 数据文件={d[f]}')
PY

# 被标成 BQSR BAM 的文件实际叫什么
python3 - <<'PY'
import csv
t2 = {r['T2_id']: r for r in csv.DictReader(open('entities/T2.csv', encoding='utf-8-sig'))}
ids = [r['T2_id'] for r in csv.DictReader(open('relations/T2_in_format.csv', encoding='utf-8-sig'))
       if r['semantic_format'] == 'DNA_ALIGNMENT_BQSR_BAM']
names = [t2[i]['file_name'].lower() for i in ids]
print(sum('bqsr' in n or 'recal' in n for n in names), '/', len(names))
print(names[:5])
PY

# 每条 data 边两端的语义格式交集
python3 - <<'PY'
import csv, collections
R = lambda p: list(csv.DictReader(open(p, encoding='utf-8-sig')))
ti, to = collections.defaultdict(set), collections.defaultdict(set)
for r in R('relations/tool_has_semantic_input.csv'):  ti[r['tool_id']].add(r['format'])
for r in R('relations/tool_has_semantic_output.csv'): to[r['tool_id']].add(r['format'])
name = {r['tool_id']: r['tool_name'] for r in R('entities/tool.csv')}
for r in R('relations/tool_relationship.csv'):
    if r['kind'] != 'data': continue
    shared = to[r['tool_id']] & ti[r['next_tool_id']]
    print(f"{name[r['tool_id']]:12} -> {name[r['next_tool_id']]:14} 交集={sorted(shared) or '空 ← 有问题'}")
PY
```
