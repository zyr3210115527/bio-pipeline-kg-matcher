# 癌种识别改由规划器承担

## 为什么改

癌种识别原本是关键词匹配：`DISEASE_ALIASES` 一张中文别名表，配上一组正则和停用词。
这条路在两轮独立评审里被打穿，而且**每个洞的修法都要新加一张表**：

| 输入 | 旧行为 | 后果 |
|---|---|---|
| `肝\u200b癌`（零宽字符） | 识别不出，`disease` 与 `disease_unresolved` 双空 | 过滤整个失效，突变景观绑到胶质瘤队列，参数齐全可提交 |
| `NSCLC` | 不在别名表，又没有「癌/cancer」后缀 | 同上，免疫浸润绑到胶质瘤 |
| `immune infiltration in liver cirrhosis` | `liver` 子串命中肝癌别名 | 肝硬化被当成肝癌，绑上 HRA001272 |
| `肝硬化患者的免疫浸润` | 双空 | 过滤失效 |
| `前列腺癌能不能参考肝癌那套流程` | 按字典序先撞上「肝癌」 | 用户问的前列腺癌被静默丢掉 |
| `胶织瘤`（错别字）、`計數矩陣`（繁体）、`肝脏肿瘤`（口语） | 都接不住 | 队列绑不上，方案不可提交 |

补表补到第五张（`_DISEASE_SUFFIXES`、`_ENGLISH_DISEASE_RE`、`_ENGLISH_STOPWORDS`、
`_NOT_IN_DISEASE_NAME`、`_GENERIC_DISEASE_WORDS`）时，补丁之间已经开始互相打架：
为了让「胰腺癌」被认出来加的后缀规则，会把「我有一对**肿瘤**和正常配对的 WES」
整段当成病名，进而拒掉一条正常的配对分析（基准 q092 就是这么挂的）。

这类问题的本质是自然语言理解，而这条链路里本来就在调 LLM。

## 怎么改的

**癌种判定跟着已有的那次规划器调用回来，不额外增加往返。** 时序上 LLM 调用
（`_top3_llm_decision`）本来就在 `_rule_intent` 之前，所以只是在同一份 JSON 里
多要一个字段：

```json
"disease": {
  "status": "matched | not_available | unspecified",
  "term": "用户原话里指的癌种",
  "study_accessions": ["只能来自提示词里的队列清单"]
}
```

**关键设计是接地到闭集，而不是让模型自由发挥。** 提示词里带上图里全部 20 个
队列（accession + tumor_type + 标题），模型只能从中挑；`_llm_disease()` 拿到结果后
逐个核对 accession 是否真实存在于 `study_by_id`，编出来的一律丢弃，`matched` 但
一个都不剩时降级为 `not_available`——宁可不给，也不能让检索随手抓一个顶上。

三种状态的下游行为严格区分：

- `matched`：`match()` 按 accession 白名单精确过滤（不再拿别名去撞 study 全文）
- `not_available`：用户点了名但图里没有，一个队列都不给，并说明「图谱里没有登记
  「肝硬化」的队列，不能用其它癌种的数据代替」
- `unspecified`：用户没提癌种，不施加队列过滤

**规则法整体删除，不保留降级。** 保留双轨会让两套语义长期漂移，而且降级路径正是
出错的那一条。规划器没跑或返回不可解析时，判定为 `unspecified` 并把
`disease_source` 标成 `unavailable`，让调用方能看出这次没有癌种约束，而不是假装
匹配上了。

删掉的东西：`DISEASE_ALIASES`、`_disease_terms`、`_disease_candidates`、
`_unmapped_disease_term`、`study_matches_disease`，以及上面那五张表。
`_match_cohorts` / `_match_files` 的第一个参数从 `disease: Optional[str]` 改成
`allowed_studies: Optional[Set[str]]`。

## 验收

八条全部通过，都是规则法做不到的：

| 输入 | 判定 | 绑定 |
|---|---|---|
| `肝\u200b癌 的 MAF 做突变景观` | matched / 肝癌 | HRA001272，可提交 |
| `NSCLC 的 TPM 做免疫浸润分析` | matched / NSCLC | HRA005191 |
| `肝硬化患者的免疫浸润` | not_available | 拒绝 |
| `immune infiltration in liver cirrhosis` | not_available | 拒绝，未绑 HRA001272 |
| `前列腺癌能不能参考肝癌那套流程做生存分析` | not_available / 前列腺癌 | 拒绝 |
| `胶织瘤 TPM 和 PFS`（错别字） | matched / 胶质瘤 | HRA000071 |
| `肝脏肿瘤的 somatic mutation 表做 oncoplot` | matched / 肝癌 | HRA001272，可提交 |
| `肝癌 HER2 表达和 PFS`（对照，不许退步） | matched / 肝癌 | HRA001272，3/3 参数齐全 |

`tests.test_question_benchmark` 96 例全部复现通过。

过程中发现一个必须记下的坑：`disease` 字段刚加进 schema 时，模型会**间歇性地整个
省略它**，此时系统落到 `unspecified`，等于悄悄关掉了癌种过滤——比报错更危险。
修法是在提示词里把它提升为规则 0a、显式声明「任何情况下不能省略」，并给出四个
覆盖三种状态的示例。加完之后上表才稳定通过。

## 补修：整卡消失与 unvalidated_parameters

### 整卡被原子链绑架

`recommendations`（目录里有没有能做这件事的业务流程）和 `candidates`（能不能拆成
可执行原子步骤）是两件事，但规划器会在拆不出原子链时把前者一并清空，理由写
「尚未原子化」。后果是目录里明明登记着的流程，用户换个说法就整个消失。

修法与 `disease` 字段同一招：把约束从规则 0 的长段落里提出来，单列为规则 0b，
明说"拆不出原子链永远不是清空 recommendations 的理由"，并点名 WGCNA、无监督聚类、
免疫浸润、驱动基因性别分层、突变景观这几个就属于"整卡现成、原子层没有"的情况，
同时说明换说法、繁体、错别字、只描述目的而不点工具名都不改变这一点。

验证（原本三条全空）：

| 输入 | 修复后 |
|---|---|
| `黑色素瘤的基因計數矩陣想做非監督式分群…`（繁体） | `rnaseq_unsupervised_cluster` |
| `结合肝癌突变清单、性别资料和样本映射，检验男女两组驱动突变频率是否不同。` | `driver_gene_gender_analysis` |
| `胶质瘤 count 表已经有了，想挖和分级挂钩的模块与枢纽基因，有现成方案不？` | `wgcna` + `wgcna_hub` |

### unvalidated_parameters

**正则长度**：`[A-Z][A-Z0-9]{1,9}` 最长只吃 10 字符，11 位的 `FAKEGENE404` 抓不到，
返回 `gene=null`。放宽到 24 位并允许连字符。这个字段的职责是把用户写了什么原样带出来
交给下游校验，不是判断它是否合法，所以宁可宽也不要漏。

**误申报**：判据原本是"描述里含'基因'就申报"，25 个流程里有 24 个中招——基因表达
矩阵、差异基因、hub 基因、突变基因 Oncoplot 说的都是分析内容，不是可传参数。改成匹配
"特定/指定/目标基因"这类明确表示"用户指定某个基因"的措辞后，精确收敛到真正接受该
参数的两个流程：`her2_pfs_survival`（特定基因，默认 HER2）和 `survival_analysis`
（指定基因突变状态）。

验证：`在黑色素瘤表达矩阵里按 FAKEGENE404 高低分组后比较 PFS。` → 申报
`gene=FAKEGENE404`；`这份肝脏肿瘤的 somatic mutation 表…做 oncoplot` → 不再申报。
